Enterprise context

Where this workload sits in a platform landing zone

An Azure landing zone has two halves: a platform landing zone (the centralized hub/platform subscriptions that provide connectivity, identity, governance, and shared monitoring) and application landing zones (the workload spoke subscriptions where teams deploy inside the platform's guardrails). This Container Apps workload is an application landing zone that peers into the platform hub — it consumes central services rather than re-creating them.

Platform landing zone

Hub & platform subscriptions

Owned by the platform team · shared by every workload

  • Connectivity: hub VNet, Azure Firewall / egress control, ExpressRoute & VPN gateways, Azure DDoS Protection Central inspection and hybrid connectivity shared across all spokes.
  • Private DNS zones (privatelink.*) Resolved centrally so every spoke reaches private endpoints consistently.
  • Identity: Microsoft Entra, domain services The primary security boundary for the whole tenant.
  • Management & security: central Log Analytics, Microsoft Sentinel, Defender for Cloud, Azure Policy Platform + security telemetry, SIEM, and governance guardrails.
  • Governance: management group hierarchy, subscription vending A repeatable way to hand workload teams a compliant landing zone.
Application landing zone

Workload spoke subscription

Owned by the workload team · deployed within platform guardrails

  • Spoke VNet + delegated subnet, peered to the hub Workload network that routes egress through the platform firewall.
  • Container Apps environment (VNet-injected, zone-redundant) The workload runtime and its network + security boundary.
  • Key Vault, PostgreSQL, storage + private endpoints Workload-owned data and secrets, reached privately over the spoke.
  • User-assigned managed identities and RBAC scope Least-privilege workload identity to its own resources only.
  • App-scoped Log Analytics (can forward to the central workspace) Application diagnostics owned and queried by the team.

Scaling to a multi-ACA fleet

When several business units or workloads run Container Apps side by side, give each its own application landing zone (subscription + environment) and share only what the platform can govern centrally. The Container Apps environment is the isolation, network, and billing boundary — so it follows the trust boundary.

One set for the whole platform

  • Hub networking, Azure Firewall egress, gateways, DDoS Central inspection and connectivity every spoke peers into.
  • Private DNS zones Consistent private-endpoint resolution across all workloads.
  • Central monitoring & governance: Log Analytics, Sentinel, Defender, Policy, subscription vending Uniform security posture and a repeatable landing-zone pipeline.
  • Optionally one Premium, geo-replicated ACR Per-team scoped tokens/RBAC, private endpoints, and image scanning + signing standardize the supply chain and cut cost.
  • Optionally one Azure Front Door Per-route and per-BU WAF policies behind a single global edge.
Keep per workload / BU

One set per application landing zone

  • Container Apps environment Same team + same trust boundary can co-locate apps via workload profiles; different BUs or compliance scopes get separate environments.
  • Spoke VNet + delegated subnet Network isolation and independent address space per workload.
  • Key Vault, databases, storage Blast-radius and data ownership stay inside the workload.
  • Managed identities and RBAC scope Identity separation so one BU can never reach another's resources.
  • App secrets/config, app-scoped Log Analytics, CI/CD identity Independent release cadence and diagnostics per team.
